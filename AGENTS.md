# AGENTS.md — Свод правил и инструкций для AI-агентов проекта

Этот файл является **главным законом** для любых AI-агентов (Antigravity, Cursor, Claude Code, Copilot), работающих в этом репозитории.
Любое отклонение от этих правил расценивается как критическая ошибка.

---

## РАЗДЕЛ 0. КОНЦЕПЦИЯ ПРОДУКТА И СМЫСЛ ПРОЕКТА (Product Manifesto & Problem Statement)

### 0.1. Главная боль пользователя (Problem Statement)
Разработчик постоянно переключается между задачами:
- Пишет код в **VS Code** или IDE.
- Запускает сборку, тесты или сервер в **WSL2 (Ubuntu/Debian)**.
- Подключается по **SSH** к удаленному серверу в облаке.
- Читает документацию или логи в браузере.

**Что происходит сейчас, когда возникает вопрос:**
1. Нужно оторваться от контекста, переключиться в браузер на вкладку с ChatGPT / Claude.
2. Вручную скопировать ошибку из терминала или кусок кода.
3. Вручную объяснить модели: *"Я сижу в Ubuntu внутри WSL2, пишу на Rust, вот мой лог..."*.
4. Получить ответ, скопировать обратно, вернуться в консоль.
5. **Результат:** Разрушение рабочего потока (*Focus Break*), потеря контекста, лишние 2–3 минуты на каждый запрос.

### 0.2. Наше решение (The Solution)
Сверхлегкий, нативный системный помощник для Windows, работающий по формуле **«Золотой триады контекста»**:

$$\text{Пакет для ИИ} = \mathbf{Паспорт} + \mathbf{Контент} + \mathbf{Промпт}$$

```
┌────────────────────────────────────────────────────────┐
│ 1. ПАСПОРТ ПРИЛОЖЕНИЯ (Win32 Metadata — собирается ВСЕГДА)
│    • Имя процесса: windowsterminal.exe / code.exe      │
│    • Заголовок окна: "server.py — Visual Studio Code"   │
│    • Подсистема: WSL2 (Ubuntu) / SSH / Windows Native  │
├────────────────────────────────────────────────────────┤
│ 2. КОНТЕНТ (Авто-определение без ручного выбора):      │
│    • Вариант А (если выделено мышкой): ТЕКСТ ошибки    │
│    • Вариант Б (если не выделено): СКРИНШОТ активного  │
│      окна через Win32 BitBlt (2–3 мс)                  │
├────────────────────────────────────────────────────────┤
│ 3. ПРОМПТ ПОЛЬЗОВАТЕЛЯ                                 │
│    • Вопрос из компактной всплывающей строки ввода     │
└────────────────────────────────────────────────────────┘
```

**Главный эффект для пользователя:** Полное отсутствие рутины. Не надо делать скриншоты сторонними программами, не надо объяснять ИИ, в какой ОС и программе вы сидите — ассистент мгновенно знает всё сам.

## РАЗДЕЛ 1. КАК ВЕСТИ ПРОЕКТ (Execution & Collaboration Protocol)

### 1.1. Запрет на фантазии и самодеятельность (Zero Hallucinated Decisions)
- **Агенту СТРОГО ЗАПРЕЩЕНО** принимать архитектурные решения, выбирать UI-концепции, шорткаты или сторонние библиотеки без прямого согласования с пользователем.
- Если требования не ясны или есть несколько вариантов реализации — **агент обязан остановиться и задать прямой вопрос**, описав плюсы и минусы на простом языке.
- Запрещено бежать вперед паровоза: мы не пишем код для шага 4, пока шаг 1 не проверен глазами пользователя.

### 1.2. Метод вертикальных срезов (Vertical Slices)
- Работа ведется **микроскопическими законченными шагами**:
  ```
  [Обсудили концепцию] ──> [Написали 20–50 строк] ──> [Собрали] ──> [Пользователь проверил] ──> [Зафиксировали]
  ```
- Каждый шаг должен заканчиваться **физически проверяемым результатом** (окно появилось на экране, команда вернула ожидаемый статус, тест прошел).

### 1.3. Железный закон доказательств (Evidence Before Claims)
- Запрещено писать «готово», «окно открыто», «баг исправлен» без свежего терминального вывода, подтверждающего это.
- Перед каждым действием агент объясняет: **ЧТО** он собирается сделать и **ЗАЧЕМ**.
- После действия агент показывает: **РЕАЛЬНЫЙ РЕЗУЛЬТАТ** команды с разбором ключевых строк вывода.

### 1.4. Абсолютный суверенитет пользователя над Git
- Агенту **СТРОГО ЗАПРЕЩЕНО** выполнять `git commit` и `git push` без прямого приказа («сохрани в коммит», «зафиксируй»).
- Никаких промежуточных микро-коммитов в процессе экспериментов.

### 1.5. Опыт индустрии и документация превыше самодеятельности (Docs & Battle-Tested Experience First)
- **СТРОГО ЗАПРЕЩЕНО** пытаться собирать системные конфигурации, схемы безопасности или низкоуровневые вызовы «из головы» или наугад с нуля.
- Перед каждым новым шагом или при возникновении нештатного поведения агент **ОБЯЗАН** обратиться к:
  1. Официальной документации используемой версии инструмента (например, Tauri v2 Docs, Microsoft Learn Win32 API).
  2. Официальным исходникам и шаблонам авторов инструмента на GitHub (например, `tauri-apps/create-tauri-app`).
  3. Проверенным боевым open-source проектам с высоким рейтингом (например, `microsoft/PowerToys`, `kunkunsh/kunkun`).
- Мы заимствуем **только проверенные эталонные кирпичи**, прошедшие боевое тестирование миллионами разработчиков, а не изобретаем велосипед на пустом месте.

## РАЗДЕЛ 2. КОД ДЛЯ НОВИЧКА С ПОДРОБНЫМИ КОММЕНТАРИЯМИ (Code Quality Standard)

Код пишется с расчетом на то, что его будет читать увлеченный разработчик-новичок, который хочет досконально понимать каждую строчку.

### 2.1. Принцип атомарности функций (Single Responsibility)
- 1 функция = 1 простое действие (обычно до 30–50 строк).
- Никаких гигантских комбайнов, делающих всё подряд.
- Понятные говорящие имена переменных на английском языке без непонятных сокращений (`active_window_handle`, а не `h`, `w`, `tmp`).

### 2.2. Обязательная документационная шапка
Каждая функция обязана иметь понятную шапку на английском языке с описанием:
1. Что делает функция простыми словами.
2. Зачем она нужна в системе.
3. Описание каждого аргумента.
4. Что возвращает и какие ошибки могут возникнуть.

Пример:
```rust
/// Queries the OS for the currently focused foreground window handle.
///
/// Why:
/// We need to know what application the user is looking at before our assistant opens.
///
/// Returns:
/// A Win32 HWND handle, or 0 if no window has focus.
pub fn get_active_window_handle() -> HWND {
    // Implementation...
}
```

### 2.3. Комментарии объясняют «ЗАЧЕМ», а не «ЧТО»
- ❌ **Запрещено:** Писать очевидный перевод синтаксиса:
  ```rust
  let mut buffer = [0u16; 512]; // объявляем буфер из 512 элементов
  ```
- ✅ **Обязательно:** Объяснять физический смысл системного действия:
  ```rust
  // Win32 API returns window titles as UTF-16 wide characters.
  // 512 units is the standard Windows buffer size to prevent title truncation.
  let mut buffer = [0u16; 512];
  ```

### 2.4. Нулевая магия (Zero Magic) и запрет на плейсхолдеры
- Запрещены скрытые глобальные состояния и хаки.
- Запрещены заглушки вроде `// TODO: дописать`, `// ... остальной код`.
- Любой фрагмент кода должен быть полным, готовым к компиляции и работе.

## РАЗДЕЛ 3. СТРУКТУРА ПРОЕКТА И KISS-АРХИТЕКТУРА (Architecture Standard)

### 3.1. Принцип KISS (Keep It Simple, Stupid)
- **Не усложняй без необходимости.** Если задача решается 20 строками стандартной библиотеки — запрещено тащить внешний тяжелый крейт или npm-пакет.
- **Отказ от чужих монолитных комбайнов.** Никаких готовых доноров с тысячами строк чужого маковского кода.
- **Минимальный стек зависимостей.** Каждая зависимость в `Cargo.toml` или `package.json` должна быть строго оправдана.

### 3.2. Изоляция и чистота каталогов
- **Корень проекта (`/`):** Содержит только файлы конфигурации и документации (`.gitignore`, `AGENTS.md`, `package.json`, `dev_diary/`).
- **Бэкенд (`src-tauri/`):** Нативный системный код на Rust. Модули разделены по ролям:
  - `commands/` — команды, вызываемые интерфейсом через IPC.
  - `system/` — прямые системные вызовы Win32 API.
- **Фронтенд (`frontend/`):** Изолированный веб-интерфейс. Никаких файлов фронтенда в корне проекта.
- **Дневник разработчика (`dev_diary/DEV_DIARY.md`):** Единый файл истории вех и принятых решений (без мусора и «дней»).

## РАЗДЕЛ 4. ПЕДАГОГИЧЕСКАЯ ПРОЗРАЧНОСТЬ ТЕРМИНАЛА (Learning-First Standard)

- **Никаких команд «вслепую»:** Агент никогда не запускает команду в терминале, не объяснив предварительно на чистом русском языке:
  1. Что это за программа (утилита).
  2. Что означает каждый переданный флаг и аргумент.
  3. Какой физический эффект в системе ожидается.
- **Разбор вывода:** Если команда вернула ошибку или статус, агент расшифровывает важные строки вывода, чтобы пользователь понимал механику работы системы.

## РАЗДЕЛ 5. УТВЕРЖДЕННАЯ АРХИТЕКТУРА И СТРАТЕГИЯ МИКРО-ДОНОРОВ

### 5.1. Формула запроса ("Золотая триада контекста")
Любой запрос к ИИ автоматически собирается из 3 обязательных компонентов:
$$\text{Пакет к ИИ} = \mathbf{Паспорт} + \mathbf{Контент} + \mathbf{Промпт}$$

1. **Паспорт (Win32 Metadata — собирается ВСЕГДА):** имя процесса (`code.exe`), заголовок окна, среда (`WSL2 Ubuntu`, `SSH`, `Windows`).
2. **Контент (Авто-определение):**
   - Если текст выделен мышкой $\rightarrow$ извлекается **выделенный текст**.
   - Если текст не выделен $\rightarrow$ делается **скриншот активного окна** через Win32 `BitBlt` (2–3 мс).
3. **Промпт:** вопрос пользователя из всплывающей строки ввода.

### 5.2. Стратегия «Микро-доноров» с GitHub
Вместо затаскивания тяжелых чужих пакетов целиком, мы берем **чистые, проверенные 20–30 строчные алгоритмы** из авторитетных open-source проектов:

| Узел системы | Проверенный донор на GitHub | Что конкретно заимствуем |
| :--- | :--- | :--- |
| **Узел 1: Чистый UI-каркас** | Официальный шаблон `create-tauri-app` | Чистое окно без маковской прозрачности, темный сплошной фон. |
| **Узел 2: Глобальный хоткей** | `tauri-plugin-global-shortcut` | Регистрация системного `RegisterHotKey` в ядре Windows (0% CPU). |
| **Узел 3: Сбор Паспорта окна** | `microsoft/PowerToys` (`PowerToys Run`) | Мгновенный опрос `GetForegroundWindow` + ToolHelp32 snapshot (< 1 мс). |
| **Узел 4: Захват выделенного текста** | `TheJoeFin/Text-Grab` / `GoldenDict` | Безопасная связка `OpenClipboard` $\rightarrow$ `SendInput(Ctrl+C)` $\rightarrow$ восстановление буфера. |
| **Узел 5: Быстрый скриншот окна** | `microsoft/PowerToys` (`TextExtractor`) | Прямой вызов Win32 GDI `BitBlt` (2–3 мс) без DirectX. |
| **Узел 6: Потоковый ИИ-клиент** | Стандартный `fetch` Stream (SSE) | Чтение чанков потока ответа от Google Gemini Flash. |

## РАЗДЕЛ 6. ПРАВИЛО GIT-ВЕТОК ДЛЯ ВЕРТИКАЛЬНЫХ СРЕЗОВ (Branch-per-Slice Rule)

Разработка каждого узла ведется **строго в изолированной тематической ветке**:
1. `feature/slice-1-base-window` — Срез 1: Базовое видимое окно без мусора.
2. `feature/slice-2-hotkey` — Срез 2: Системный хоткей скрытия/показа с фокусом.
3. `feature/slice-3-passport` — Срез 3: Win32 модуль Паспорта активного окна (WSL2/VS Code).
4. `feature/slice-4-content-capture` — Срез 4: Захват выделенного текста и скриншота BitBlt.
5. `feature/slice-5-gemini-streaming` — Срез 5: Стриминг ответа нейросети.

**Правило перехода:** Агенту СТРОГО ЗАПРЕЩЕНО переключать ветку или переходить к следующему срезу, пока текущий срез не проверен физически пользователем на экране.
